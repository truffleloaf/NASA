# Backend — independent 40 m terrain validation

This directory is the **independent validation pipeline** for the Lunar Mission Navigator.
It is not the source of the shipped frontend data, and it is not a web service.

The product under `public/data/` — `manifest.json`, `ephemeris/*.json`, `horizon/*.json`,
`terrain/polar-1024.{bin,json}`, `validation.json` — is generated by the repository-root
`scripts/` from the **80 m** `LDEM_80S_80M` DEM. This backend runs a separate **40 m**
`LDEM_85S_40M` implementation with its own projection, ephemeris cache and raymarcher, so
the shipped horizons and the annual numbers have an independent cross-check.

`cross_product.py` is the bridge: it reads the shipped 80 m assets, computes the same
1° skyline from the 40 m DEM, clamps both sides to the legacy 0° convention, and prints
the comparison documented in `docs/DATA.md`.

## Why there is no API server

- `AGENTS.md` rule 2: *"No new runtime network calls. All data ships in `public/data/`."*
- `next.config.ts` uses `output: "export"`, so the deployed site is static — there is no
  process to host a Python server in.

The frontend and this backend therefore meet at **files and checks**, not HTTP. A thin local
FastAPI wrapper could be added later for development, but it is not part of the deployed path
and must not become a runtime dependency.

```

│  ├─ intervals.py            boolean runs, coverage, longest gap, edge truncation

│  ├─ run_horizon.py          horizon profile for the candidate sites + self-checks
│  ├─ run_annual.py           full-year visibility, clamped and unclamped (Phase 2)
│  ├─ cross_product.py        shipped 80 m vs independent 40 m terrain table
│  ├─ check_convergence.py    ray step and ray range sensitivity (unclamped skyline)
│  ├─ demo_geometric.py       three-site Sun/Earth comparison, no terrain
│  └─ check_frontend_tests.py run the frontend's npm test/typecheck/build
└─ data/                      generated, not committed (see data/README.md)
```

## Run

Requires Python 3.10+ and `numpy`; nothing else — network access uses `urllib` from the
standard library. Use a virtual environment so the interpreter and package versions are
pinned, because the numbers below only reproduce on a known toolchain:

```sh
python -m venv .venv
.venv/Scripts/python -m pip install -r backend/requirements.txt    # Windows
# .venv/bin/python -m pip install -r backend/requirements.txt      # POSIX
```

The figures in this file were produced with **Python 3.15.0 and numpy 2.5.4**. Record the
versions you use if you re-derive them; a bare `python` on PATH may not have `numpy` at all.

Current validation path:

```sh
.venv/Scripts/python backend/pipeline/fetch_dem.py             # download the 115 MB DEM (resumable)
.venv/Scripts/python backend/pipeline/run_horizon.py           # horizon profiles + projection/curvature self-checks
.venv/Scripts/python backend/pipeline/run_annual.py            # full-year visibility, clamped and unclamped
.venv/Scripts/python backend/pipeline/cross_product.py \
    --source backend/data/dem/ldem_85s_40m.img \
    --label  backend/data/dem/ldem_85s_40m.lbl --check        # shipped 80 m vs 40 m table
.venv/Scripts/python backend/pipeline/check_convergence.py     # ray step and ray range sensitivity
.venv/Scripts/python backend/pipeline/check_frontend_tests.py  # npm test/typecheck/build on public/data
```

`cross_product.py` reads the frontend's committed `public/data` assets, so run it from the
repository root after `npm ci`/build. It accepts `--assets` to point at another checkout.

CI (`.github/workflows/backend-data-check.yml`) runs `cross_product.py --check` when
`public/data/`, `backend/`, `scripts/` or `docs/DATA.md` changes. It caches the 40 m DEM and
then verifies that the check did not modify `public/data/`.

Historical/auxiliary commands (they do **not** write `public/data`):

```sh
.venv/Scripts/python backend/pipeline/demo_geometric.py        # three-site Sun/Earth comparison, no terrain
```

The old exporter (`export_data.py`), its checker (`check_export.py`), the old window
scripts (`windows.py`, `scan_windows.py`) and the `backend/export/data/` product were
removed. If `public/data` needs regeneration, run the root `scripts/` only; the backend has
no writer for it.

`run_annual.py` and the other ephemeris users read the cache in `data/horizons/`. If it is
absent they fetch from JPL and write it, so the first run needs network and later runs do not.

## Data sources

| Source | Used for | Reference |
| --- | --- | --- |
| JPL Horizons (DE441) | topocentric Sun and Earth az/el from a lunar site | <https://ssd.jpl.nasa.gov/horizons/> |
| LRO / LOLA GDR | validation terrain, 40 m/pixel, 85°S–90°S | <https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/data/lola_gdr/polar/img/> |
| LRO / LOLA `LDEM_80S_80M` | shipped frontend terrain, 80 m/pixel, 80°S–90°S; generated by root `scripts/`, not this backend | <https://imbrium.mit.edu/DATA/LOLA_GDR/POLAR/IMG/LDEM_80S_80M.IMG> |
| PDS `dsmap_polar.cat` | authoritative polar-stereographic transformation | <https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/catalog/dsmap_polar.cat> |

Horizons is queried with `CENTER='coord@301'`, `COORD_TYPE='GEODETIC'`,
`SITE_COORD='lon,lat,alt_km'`, `QUANTITIES='4'`, `APPARENT='AIRLESS'`. The result is the
airless apparent azimuth and elevation of the body centre, already corrected for
light-time, stellar aberration and gravitational deflection. The Moon has no atmosphere,
so no refraction correction applies.

## Elevation convention

`LDEM_85S_40M` stores 16-bit little-endian integers; `height_m = DN * 0.5`, measured
relative to a reference radius of 1737.4 km (`OFFSET` in the product label). The label
also gives `LINES = LINE_SAMPLES = 7584`, `MAP_SCALE = 40 m/pix`,
`LINE/SAMPLE_PROJECTION_OFFSET = 3791.5`, polar stereographic, centre latitude −90°,
centre longitude 0°, positive east.

## Projection orientation

`dsmap_polar.cat` states the orientation in words rather than only in equations:

> In the south, Longitude 0 extends straight up from the center, and Longitude 90 East
> extends to the right.

So on this map, with `dx` positive to the right and `dy` positive upwards:

```
lon = 90° − atan2(dy, dx)      →  up = 0°, right = 90°E, down = 180°, left = 270°
```

`dem.py` implements this as `Convention(handed=-1, offset_deg=90)`. Two independent checks
confirm it: all four image corners map to latitude −82.936° (the value predicted from
`MAP_SCALE` and the image size), and a landmark fit places the Shackleton crater centre at
89.654°S 128.31°E, consistent with published coordinates.

## Validation results

Full year 2026, 1-hour step, 8761 samples. **These tables use the legacy clamped-0°
convention at a 0 m observer.** The shipped UI keeps negative skyline angles, evaluates the
Sun at 2 m and Earth at the selected mast, and therefore reports 30.3 % / 44.7 % / 46.0 %
sunlight for the three sites, not the clamped numbers below. `cross_product.py` compares
both conventions explicitly; do not quote this table as the UI's values.

**Control site — Shackleton crater floor, 89.654°S 128.31°E.** This location is known to be
permanently shadowed. It is the end-to-end test of the whole chain.

| | |
| --- | --- |
| site elevation | −2771 m |
| terrain horizon | +20.2° … +22.4° (median +21.2°) — a bowl, as expected |
| sunlit, with terrain | **0.0 %** |
| Earth visible, with terrain | **0.0 %** |

Getting exactly zero here requires the projection, the DEM sampling, the curvature term,
the horizon search, the ephemeris and the masking to all be correct at once. It does *not*
pin down the sign of the curvature term: a 21° bowl is set by terrain a few kilometres away,
where that term is worth a couple of tenths of a degree either way. See "Curvature sign" below.

**Candidate sites.** Rays traced to 150 km.

| | Shackleton 89.90°S 0.00°E | Malapert 85.99°S 2.30°E |
| --- | --- | --- |
| site elevation | +629 m | +5148 m |
| terrain horizon | 0.0° … +22.4° (median +1.9°) | 0° … +3.8° (median +0.7°) |
| sunlit, geometry only | 52.6 % | 51.6 % |
| sunlit, with terrain | **23.7 %** | **36.6 %** |
| longest continuous sunlit | 330 h (13.8 d) | 347 h (14.5 d) |
| Earth visible, geometry only | 46.3 % | 66.6 % |
| Earth visible, with terrain | 46.2 % | **54.7 %** |
| sunlit **and** Earth visible | 16.5 % | **22.9 %** |

**Curvature sign.** The first version of this table was wrong by a factor of eight: it
reported 2.8 % and 0.9 %. `elevation_angle` had `(R+h_t) − (R+h_s)·cos d` over
`(R+h_s)·sin d`, which lifts distant terrain instead of dropping it — at 150 km an
equal-height point came out at +2.47° instead of −2.47°. The pole's Sun never rises above
+1.6°, so a few tenths of a degree of spurious elevation removed most of the light. The
control site kept reporting 0.0 % throughout, which is exactly why it did not catch this.
`horizon.selfcheck()` now checks the analytic cases and `run_horizon.py` aborts if they fail.

**Invariants.**

1. **Monotonicity (clamped convention)** — terrain-aware visibility never exceeds geometric
   visibility (`el > 0°`). Passes for all three sites. This invariant is only valid while the
   skyline is clamped; with negative skyline angles a body below the 0° tangent can still be
   visible, which is why `run_annual.py` now reports both and checks `unclamped ≥ clamped`
   instead of applying the geometric bound to the unclamped numbers.
2. **Known geography** — the crater floor is fully dark. Passes (0.0 %) in both conventions.
3. **Azimuth wrap** — horizon at 0.5° and 359.5° differ by 0.036°. Passes.

Additional numerical checks: the vectorised sampler agrees with `dem.Projection` to
1.8 × 10⁻¹² pixel; all four image corners map to −82.936°; an equal-height ray comes out at
−r/2R to within 3.5 × 10⁻¹²° from 1 km to 150 km.

Ray range turned out not to matter once the curvature sign was fixed: 50 km, 150 km and
250 km traces agree to 0.000° at the pole. The earlier claim that range mattered a lot was an
artifact of the same sign error.

## Current product (not written here)

The shipped assets are generated by the repository-root `scripts/` and committed under
`public/data/`:

```
public/data/manifest.json
public/data/ephemeris/{shackleton,malapert,de-gerlache}.json
public/data/horizon/{shackleton,malapert,de-gerlache}.json
public/data/terrain/polar-1024.bin
public/data/terrain/polar-1024.json
public/data/validation.json
```

`docs/DATA.md` is the contract: 80 m DEM, 8,761 hourly ephemeris rows with angular
diameters, 2 m and 20 m skyline profiles (negative angles kept), 1° azimuth bins, and
`elevationMeters + 2 m` observer altitude. The browser computes windows from those rows and
profiles; nothing is fetched from a backend at runtime.

`cross_product.py` is the only backend code that reads this product. It is a check, not a
generator: it compares the shipped 80 m horizons with an independent 40 m recomputation.

## One writer only

`public/data/` has exactly one writer: the repository-root `scripts/`. The old
`export_data.py` and `backend/export/data/` were removed, so the backend cannot accidentally
produce a second, divergent asset set. `cross_product.py` is read-only over `public/data`.

If you find a backend script that writes into `public/data/`, treat it as a bug: the frontend
build imports `manifest.json`, `terrain/polar-1024.json` and `validation.json` statically, and
a second writer would silently change what ships.

## Findings that affect the frontend

All fractions below use the legacy clamped-0° / 0 m convention. The shipped UI uses the
unclamped 2 m skyline; `cross_product.py` is the place to compare conventions.

- At 89.90°S 0.00°E the site is **23.7 % sunlit over a year in the clamped convention**
  (30.3 % in the shipped unclamped convention) — in runs of up to 13.8 days. The terrain
  horizon is 0.0° to the north-west and reaches +22.4° to the south-east, so the site is lit
  while the Sun is on the open side of each lunar day and dark when it crosses the crater
  wall. The point is about 12.6 km from the Shackleton centre (crater radius about 10.5 km),
  i.e. beyond the rim on the far side. “Shackleton region” is therefore the honest name; this
  is a partly shadowed site beside the crater, not the illuminated rim crest. If the product
  means to show a favourable site, the coordinate should be reconsidered — the published
  high-illumination points are on the crest itself.
- Malapert beats Shackleton on combined sunlight and Earth visibility, but no longer by an
  order of magnitude: **22.9 % vs 16.5 %** clamped. Geometry alone barely separates them
  (51.6 % vs 52.6 % sunlit, 66.6 % vs 46.3 % Earth visible); terrain does. Shackleton keeps
  only 45 % of its geometric sunlight, Malapert 71 %.
- Earth visibility from the pole is dominated by libration in latitude (±7.0° swing), not
  by terrain. A week with no Earth visibility is expected and is not a bug.
- The shipped product adds the third site, de Gerlache; the 40 m pipeline only checks the
  overlapping part of its sky (256 / 360 complete azimuths). See the cross-product table.

## Known caveats

- `public/moon-height.jpg` in the frontend is `ldem_3_8bit`: 3 pixels per degree (about
  10 km/pixel) and 8-bit. It is a texture and must never be used to compute a horizon.
- Sun and Earth are extended discs, not points. The Sun subtends 0.266° and the Earth
  about 0.951° as seen from the Moon; at the poles, where both graze the horizon, the
  choice of centre versus limb changes results materially. `run_annual.py` reports both.
- Lunar curvature must be removed when testing terrain obstruction:
  `drop(r) = r^2 / (2 * 1737.4 km)`, which is about 115 m at 20 km. Omitting it
  systematically overestimates obstruction. `horizon.py` uses the exact spherical form.
- For Malapert, 155 of 360 azimuths cannot reach 95 % of 150 km because the ray leaves the
  85°S–90°S DEM; the shortest stops at 30 km. Its 40 m horizon is therefore a lower bound in
  roughly half the sky, so its true illumination is somewhat lower than reported. The shipped
  product uses the 80 m `LDEM_80S_80M` product instead, which covers 80–90°S and removes this
  truncation. Re-running the 40 m cross-check against `ldem_80s_40m` (462 MB) would also
  remove it, at a large download cost.
